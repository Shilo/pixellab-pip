# MCP Platform Tools

Use this reference for PixelLab MCP tools that operate on projects, sandboxes, deployed agents, chat conversations, help, feedback, or Creator gallery/save-back workflows rather than direct asset generation.

Official MCP docs currently expose platform helpers such as `list_projects`, `manage_project`, `add_to_project`, `remove_from_project`, `chat_*`, `sandbox_*`, `search_help`, `agent_feedback`, `agent_list`, `agent_inspect`, `agent_talk`, `search_knowledge`, `list_jobs`, `wait_for_jobs`, and `cancel_job`, plus room tools `create_room`/`get_room`/`list_rooms`/`delete_room`/`cut_out_room_furniture` (also public REST v2), Creator gallery/asset tools `list_images` and `save_to_asset` (`save_to_asset` also has REST `POST /save-to-asset`), and stored-asset helpers `rename_asset`, `manage_state`, `set_canvas_size`, `mirror_animation`, `expand_object_to_8_directions`, `import_object`, `import_tiles`, and `export_asset`. Map tools include `inpaint_map` and `edit_map_areas`. These are public MCP tools, not REST v2 endpoints, except where noted. Version 0.4.123 makes Game Builder available to Tier 1+ subscribers; use the visible Game Builder product for that workflow and only use the public project/chat/sandbox helpers when the user requests an approved project-scoped action. Generation tools that accept `project_id` can link results to that Game Builder context, including `edit_image`, `create_normal_map`, `animate_image_pixminimax`, and `animate_with_skeleton_v3`, but there is no documented dedicated REST v2 Game Builder endpoint.

## Safety Rules

- Use `search_help` freely for PixelLab MCP usage questions and documentation Q&A. `search_knowledge` is a free read against a Phaser/game-dev knowledge base — use it only for that subject, not as a general search.
- `list_jobs` is a free read of your active background jobs; use it when a job ID was lost or the user asks what is still running.
- `remove_map_object` with `placement_id` removes one map placement; with `asset_id` it removes every placement of that asset from the map. Inspect the map and enumerate affected placements before a user-approved bulk removal.
- `cancel_job` discards the pending result. Ask before cancelling, naming the job and what it was producing; billing claims and the REST/MCP disagreement are canonical in `job-lifecycle.md`.
- `list_images` is an account gallery read. Use it only when the user asks to inspect or search that gallery, and do not treat a missing or stale gallery listing as permission to replace anything.
- Room tools (`create_room`, `get_room`, `list_rooms`, `cut_out_room_furniture`, `delete_room`) also have REST v2 routes. `list_rooms` is an account read; use it only when the user asks to find or choose an existing room (default 20 per page, `limit` 1–100 and `offset`). `get_room` returns the selected room's art and walkable areas. `delete_room` is destructive and refused while a cut runs or a saved arrangement uses its pieces; get explicit approval. See `scenes-and-backgrounds.md`.
- `save_to_asset` (or REST `POST /save-to-asset`) is free and does not start a generation, but saving to an existing character rotation, object direction, animation direction, gallery image, or tileset sheet replaces remote content. Read the relevant asset first, list the exact target and consequence, and obtain explicit approval before using an existing target. `gallery:new` is additive; it may include `description` and `name`. Inputs can be a Workbench result, raw-image job reference, URL/data URL, or base64; prefer a returned PixelLab job/reference over re-uploading a transformed local copy. A PNG strip is still one frame: for animation use a GIF (one shared duration), multi-image `job:<id>`, or multiframe Workbench result, then verify the saved count/timing. REST returns `previous_frames`, which can be posted back to the same target as the undo.
- `manage_project` creates a folder, renames a folder or game project, or deletes a folder. Deleting a folder keeps its assets; game projects are deleted only on the website. Name the target before a delete.
- `rename_asset`, `manage_state` (`duplicate`/`ungroup`), `set_canvas_size`, and `mirror_animation` are free stored-asset edits. Renaming and duplicating add or relabel content; ungrouping and deleting a state remove a state from its group, so confirm the target first. `expand_object_to_8_directions` costs 10–25 generations and then waits in `review-expansion` until the directions are kept or discarded.
- `import_object` and `import_tiles` are free and add your own PNG art as normal saved assets; nothing is generated. `export_asset` returns a free ZIP, spritesheet, `.aseprite`, or GIF download link.
- Map helpers `inpaint_map` (5 generations up to 96px, 6 up to 208px, 9 up to 256px, by the area's longest side; not for sidescroller maps or maps with tile layers) and `edit_map_areas` (declare walkable/blocking layers by terrain) follow the same approval rules as other map edits. Preview destructive terrain or tile erasure with `dry_run` where the tool offers it.
Target syntax is `character:<id>:<direction>`, `object:<id>` or `object:<id>:<direction>`, with `:<group-id>` added for an animation direction; use `gallery:<id>` to replace a gallery image or `gallery:new` to add one. See the live tool schema for the exact input forms.
- Use `agent_feedback` only when the user wants to report feedback or after you have a concise, non-secret issue report. Do not include bearer tokens, private prompts, raw files, account data, or unrelated local paths.
- Treat `list_projects`, `list_rooms`, `chat_list_conversations`, `chat_get_messages`, `agent_list`, and `agent_inspect` as account or project data reads. Ask for approval before reading them unless the user directly asked for that exact information.
- Treat `chat_send_message`, `agent_talk`, `add_to_project`, `remove_from_project`, `sandbox_create_session`, `sandbox_bash`, `sandbox_run`, `sandbox_write`, `sandbox_edit`, `sandbox_sync`, `sandbox_read_image`, and `sandbox_destroy_session` as state-changing or potentially sensitive actions. Get explicit approval for the specific target and action before calling them. `add_to_project` files an owned character, object, tileset, map, room, or gallery image (from `list_images`) into a game or website folder project; `remove_from_project` removes an asset, including a room, from a project. `sandbox_write` defaults to `force: true` and overwrites silently — read the path first when the file may already exist.
- For `sandbox_destroy_session`, `sandbox_deploy_worker`, `sandbox_undeploy`, `sandbox_playtest`, destructive deletes, git syncs, or any command that may publish, overwrite, delete, or spend credits, clearly name the target and consequence before asking for approval. `sandbox_deploy_worker` and `sandbox_undeploy` are outward-facing publish/delete actions — name the project and branch when asking. `sandbox_undeploy` accepts a project slug or ID, but always identify the target explicitly; do not rely on its optional target fields being omitted.
- Do not use PixelLab sandbox tools to bypass the user's local repository, approval, or secret-handling rules. If a task is ordinary local coding work, use the local workspace unless the user explicitly requests a PixelLab sandbox.
- `sandbox_bash.timeout` is optional: normal default 300 seconds; a command running `wrangler deploy` gets at least 1200. Allow for that deployment time without resubmitting or treating a client timeout as publish failure.
- Do not paste secrets, raw environment dumps, private traces, full chat transcripts, or full agent traces into reports. Summarize only the minimum needed to answer or debug the user's request.

## Reporting

Report the MCP tool used, the project/session/conversation/agent identifier only when needed for follow-up, whether the action was read-only or state-changing, and any next step that needs user approval.
