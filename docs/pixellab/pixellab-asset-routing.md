# PixelLab Asset Routing

Last reviewed: 2026-11-07. Routing preferences reconciled with the [evidence review](../tools/pixellab-mcp-docs-vs-pip-skill.md); linked generation spikes retain their original conditions.

Purpose: map plain-language asset requests to the PixelLab workflow family most likely to satisfy the user without asking them to know PixelLab's internal product vocabulary.

PixelLab requests usually start as plain asset goals: "make a character," "generate a tileset," "edit this sprite," or "create UI." Pip should classify the asset intent first, then choose the PixelLab surface and endpoint/tool family.

Use this as human-facing routing background, not as a frozen schema. The [skill router](../../skills/pixellab-pip/SKILL.md) and its operational references define current runtime decisions. Refresh official docs for exact current parameters, result shapes, model/mode availability, pricing, and SDK coverage.

**Pro Flash is a separate beta family.** The public MCP/REST docs add one-image, eight-view character, one/eight-view object, one-image edit, masked-edit, and pixel-art conversion operations. The MCP guide documents a 5/6/9-generation longest-side ladder for creation/edit/inpaint and separately billed eight-view rotations; REST describes a provisional five-generation first image. Pixel-art conversion costs 6 generations per image and detects native scale/output size. Quotes remain provisional; use the free MCP capability price split or REST cost lookup. See the [Pro Flash operational reference](../../skills/pixellab-pip/references/pro-flash.md) for supported needs and cost/quality tradeoffs; the product name proves no quality advantage.

## Asset Intent Map

| User intent | Preferred route | Notes |
|---|---|---|
| Character, player, NPC, enemy, creature | MCP character tools when configured; REST v2 character endpoints for code or exact control. | Managed characters carry identity, directions, states and animations; a general-image sprite is a different output. Ordinary humanoids use Pip's v3 preference; standard remains supported for lowest-cost text creation. Text-only quadrupeds can use standard or Pro/Flash directly, without generating a reference merely to use v3. Reuse a suitable supplied sprite through matching v3 reference controls. Pro concept art seeds a look rather than preserving pose/canvas; see [image roles](../../skills/pixellab-pip/references/image-input-roles.md). Explain the chosen cost/style tradeoff and inspect every requested facing; no model guarantees adherence. |
| Portrait to character or character to portrait | MCP portrait-character tools when configured; REST v2 `portrait-character-pro` for code or exact control. | This is an image conversion workflow. Use `portrait_to_character` for a bust portrait source and `character_to_portrait` for a full-body character source. |
| Talking portrait, mouth shapes, talking GIF, or lip-sync plan | MCP talking-portrait tools when configured; REST v2 for code, stateless lip sync, or exact control. | Attach a portrait, generate one mood's visemes with the only paid call, then render a free synchronous GIF or request a free timing plan. REST `/lip-sync` alone supports stateless `viseme_count`. Preserve dialogue verbatim. |
| Character state or outfit/layer change | MCP character-state tools when available; REST v2 state/edit routes when exact control is needed. | Clarify whether the output should preserve identity, change pose/state, or generate a new design. |
| Character animation | Select matching templates, fitting v3 free-form motion or PixMiniMax under [Animation → Route Choice](../../skills/pixellab-pip/references/animation.md#route-choice); honor explicit engines/counts. | Default unspecified direction to `south` for a preview; retain an already-approved wider scope. Batch already-approved template facings only with identical controls. Inspect motion and each facing; service defaults do not establish a universal quality winner. |
| Object, prop, pickup, weapon, furniture that is not an icon or icon sheet | MCP object tools when configured; REST v2 object endpoints for code or exact control. | Infer object for standalone props, furniture, weapons, and managed reusable objects. Do not route inventory item icons, equipment icons, loot icons, pickup icons, or transparent RPG item-icon sheets through object generation. |
| Object animation or object state | MCP object animation/state tools when available; REST v2 object animation/state endpoints for direct API use. | Treat reusable objects differently from one-off generated images. |
| Top-down terrain tileset | MCP top-down tileset tools or REST v2 tileset endpoints. | Usually means terrain/autotile/Wang-style tileset. |
| Sidescroller/platformer tileset | MCP sidescroller tileset tools or REST v2 sidescroller tileset endpoints. | Distinct from top-down terrain and individual tile variants. |
| Individual tile variants | MCP tiles-pro tools or REST v2 tiles-pro endpoints. | This is different from a full terrain tileset. Clarify "tiles" vs "tileset" when ambiguous. |
| Isometric tile | MCP isometric tile tool or REST v2 isometric tile endpoint. | Ask whether the user wants one isometric tile or a full tileset when the wording is ambiguous. |
| Connectable path/road tile set | MCP `create_path_tiles` or REST v2 `create-tiles-pro` (`tile_feature: "roads"`). | Shares the tiles-pro get/list/delete tools; no dedicated getter. |
| Building kit (floor, connectable walls, doorways, pillar, stairs) | MCP `create_building_kit` or REST v2 `create-tiles-pro` (`tile_feature: "building"`). | Shares the tiles-pro get/list/delete tools; no dedicated getter. |
| Skill, ability, spell, action-bar, or hotbar icon | Ordinarily one native-size Pixen image for one small icon; compare concept-specific calls/assembly with Pro for sheets, references or variety. | See [Icons](../../skills/pixellab-pip/references/icon.md). Preserve the requested final sheet, subjects and cell sizes; `32x32 icons` describes each cell. Pro candidates are alternatives, not guaranteed distinct named concepts. The [historical skill-icon spike](pixellab-skill-icon-generation-spike.md) supports its tested backgrounded sheets, not a universal single-icon default. Retain rich backgrounds when wanted; UI tools fit slots/buttons/containers themselves. |
| Inventory item, equipment, loot, pickup, consumable, or transparent RPG item icon | The same single-icon versus exact-set decision in [Icons](../../skills/pixellab-pip/references/icon.md). | Use requested transparency and style controls. Verify every named item, native readability and exact cell coverage. Object routes showed weak small-icon clarity in scoped tests; that is a preference, not proof they cannot make icons. Do not force a palette/detail change or substitute generic variety for an exact list. |
| General image, standalone sprite, icon, concept that is not a skill icon or item icon | MCP `create_image_pixflux`/`create_image_pixen`/`create_image_pro` + `get_image` when MCP-first (same model choice as REST, minus BitForge and multi-image style reference); REST v2 image generation otherwise. | Route skill/ability/spell/action-bar/hotbar icons through the skill-icon reference, and inventory/equipment/loot/pickup icons through the item-icon reference. |
| Exact hex palette or color cap | The requested asset's own route when it accepts MCP `palette`/`palette_name`/`max_colors` or REST `target_palette` — since 2026-10-19 most Pro-family image, character, object, tile, UI, portrait, Pro Flash, and Pro animation routes do. | Some routes accept it only in `mode="pro"`; MCP `animate_character` has no palette field, while REST managed animation accepts `target_palette` in Pro, Skeleton v3, v3, and PixMiniMax modes. Palette-constrained managed character animation remains REST-only. With a REST style image, set `style_options.color_palette=false`. See [Create Image Pro](../../skills/pixellab-pip/references/create-image-pro.md) for the route list. |
| Model-authored pixel-level draw/edit/inspect/animation commands | MCP `pixelart_workbench` when the user explicitly requests Workbench or the operation fits its command workflow. | MCP-only; accepts supported PixelLab IDs or image references, not local paths; no public REST endpoint. Use regular image-generation routes for open-ended image creation. See [PixelArt Workbench](../../skills/pixellab-pip/references/pixelart-workbench.md). |
| Background, scene, title image | MCP general-image tools when visible; REST v2 background/image generation for code or exact control. | REST includes `create-image-pixflux-background`; map/editor semantics require their own surface. A small [model benchmark](../pixellab-image-model-benchmark-results.md) favored PixFlux for subject-less backdrops and Pixen for full scenes with a subject; it also found weak Pixen props and BitForge art. Two seeds and one reviewer establish neither universal rankings nor a fixed cost/value ratio. Choose supported controls, inspect the requested result and disclose the current price. |
| UI, HUD, button, panel, menu | MCP `create_ui_asset` + getter for structured pieces when visible; REST `/create-ui-asset` for code/exact controls or fallback. REST `/generate-ui-v2` fits loose UI images. | Check selected geometry limits and visible alpha bounds, preserve intentional padding/anchors, and identify usable cropped pieces separately from raw/audit files. Simple loose pairs can also work through general-image tools; they do not establish structural/nine-slice capability. See [UI surface research](pixellab-ui-generation-surfaces-research.md) and the current [router](../../skills/pixellab-pip/SKILL.md). |
| Pixel font, bitmap font, font atlas, generated game font | MCP font tools when configured; REST v2 `generate-font-pro` for code or exact control. | Use this for actual font generation with weight, glyph size, and optional font family name. Do not treat it as a generic lettering image route. |
| Image edit, inpaint, remove background, resize, convert to pixel art | MCP `edit_image_pixen` (1 generation) for a small text-instruction edit, `edit_image` (Pro) for larger/reference edits, `inpaint_image` for masked edits, and `image_to_pixelart` for fixed-size conversion. With no output size requested, use the older REST-only Pro converter, which detects native scale; Pro Flash is a separate six-generation MCP/REST alternative when requested. Remove background and resize remain REST-only. | Supplied images are optional unless the selected route requires image fields. For a fixed output size within current `output_size` limits (now up to 512x512, from inputs up to 2048x2048), use normal `image-to-pixelart`. If the requested size is outside those limits, the older Pro route detects output size but cannot guarantee an exact dimension; verify the result, then ask before using PixelLab `resize` or local nearest-neighbor/canvas resize/pad/crop. |
| Generate a normal map for a sprite or animation | MCP `create_normal_map` + `get_image` when visible; otherwise REST v2 `POST /normal-map`. | The input is a PNG sprite or an equal-frame horizontal strip; output has the source dimensions, with alpha 255 on visible sprite pixels and 0 elsewhere. REST supports 8–512 px per frame and up to 32 frames in endpoint prose; choose OpenGL by default or DirectX for Unreal. Both surfaces take `mode`: `lite` (default) costs 0.1 generation and `pro` 0.5, charged only when delivered; set `kind` for sidescroller, isometric, and UI art. Creator availability was announced in 0.4.130; its exact UI flow is not documented. |
| Animate an existing image/sprite directly (no managed character/object) | MCP `animate_image_pixminimax` or REST `/animate-pixminimax` by default when constraints fit; use the selected engine's frame anchors for a tween. | Explicit engines and exact-count/cost exceptions follow [Animation → Route Choice](../../skills/pixellab-pip/references/animation.md#route-choice). Raw v3 remains MCP `animate_image` / REST `animate-with-text-v3`. |
| Animate from Skeleton v3 keypoints (raw image) | MCP `animate_with_skeleton_v3` for a supplied image plus per-frame keypoints when visible; otherwise REST `POST /animate-with-skeleton-v3`. | Beta, 3–15 pose sets, max 256×256. The refreshed REST/MCP descriptions no longer state a Tier 1 gate. The legacy `/animate-with-skeleton` endpoint still requires exactly three pose sets. See [Skeleton and Template Animation](../../skills/pixellab-pip/references/preset-skeleton-template-animation.md). |
| Animate a managed character with Skeleton v3 | Custom motion by default for an explicit Skeleton v3 request on a humanoid; retain a preset only when requested. | MCP `animate_character(mode="skeleton-v3")` discovers instructions for free, then accepts humanoid `poses`/`scale` or a tool-described `move`; its documented move lists also support dog, cat, horse, bear, and lion templates. REST `/animate-character` and `/characters/animations` instead generate one shared motion from action text; no pose fields. Custom motion uses 3–15 frames; reuse the group for later directions. See [the operational contract](../../skills/pixellab-pip/references/preset-skeleton-template-animation.md#skeleton-v3-custom-motion-managed). |
| PixMiniMax animation | For a stored character, MCP `animate_character(mode="pixminimax")` or REST `/animate-character` / `/characters/animations`; for supplied raw frames, MCP `animate_image_pixminimax` or REST `/animate-pixminimax`. | Both routes are beta; the raw MCP tool and REST state no Tier 1 gate, and MCP `animate_character` explicitly says PixMiniMax is available on every tier. Managed animation uses a stored character and supports 4–40 generated frames in multiples of four; raw animation takes first/optional last frames and returns `frame_count+1` images. The public API catalog identifies the raw REST operation as powered by MiniMax H3 and lists the plugin label “Animate with text (PixMiniMax)”; the MCP guide does not repeat that provider attribution, and managed mode remains undisclosed. See [Animation](../../skills/pixellab-pip/references/animation.md). |
| Get a PixelLab image description or visual answer | REST `POST /image-to-text`. | REST-only; returns a generic image description or custom image-grounded answer, not an image. It is not a required pre-step to a target-specific prompt enhancer. Typical usage is estimated at 0.09 generations; actual usage varies with answer length. See the [image-to-text research spike](pixellab-image-to-text-research-spike.md). |
| Multi-image edit or combine references | MCP `edit_image` when MCP-first (preferred `image_urls`, or inline base64; optional reference URL/base64 switches to reference mode); REST v2 `edit-images-v2` otherwise. | MCP `edit_image` matches the `edit-images-v2` (Pro) workflow, not base `edit-image`. Aseprite's observed `generate-multi-edit` operation is an undocumented internal endpoint, not a public REST route. |
| Style reference or consistent-style generation | Create Image from Style Reference (Pro) (`generate-with-style-v2`) or another documented style/reference route. | Use Create Image from Style Reference (Pro) (`generate-with-style-v2`), Create Image Pro (`generate-image-v2`) style/reference fields, or documented image-model style fields as appropriate after checking current docs. In one focused house investigation, 24 reviewed Create Image (New) / Pixen (`create-image-pixen`) outputs failed to hold the requested top-down view. The user additionally reported the same practical failure with init-image guidance and Create Image Pro (`generate-image-v2`), and success with Create Image from Style Reference (Pro) (`generate-with-style-v2`). See [PixelLab Top-Down House Generation Routing Spike](pixellab-top-down-house-generation-routing-spike.md). Treat this as subject-specific observed routing evidence, not a universal model guarantee. |
| Canny/sketch, pose-guided image, depth/image-to-image | Visible website/editor/Aseprite workflow for exact Canny/Pose/Depth behavior; REST v2 only for an approximate documented image/init/reference workflow after explaining the difference and getting approval. | No exact public REST v2/MCP Canny, Pose, or Depth endpoint was documented. Observed Aseprite operation names include `generate-general-canny`, `generate-general-pose`, and `generate-pixelart-flux`; treat them as undocumented internal endpoints unless they appear in PixelLab's public REST v2 docs/OpenAPI or MCP docs as supported programmatic endpoints/tools. |
| PixelLab experimental Create VFX page | Use the visible `https://www.pixellab.ai/create-vfx` page only when explicitly requested; MCP `vfx_workbench` is a separate agent-authored workbench. | REST `POST /vfx` is documented as the same effects artist; the docs do not establish that `vfx_workbench` shares the page's implementation. |
| Add a static VFX/effect/trail/aura to an existing sprite | REST v2 image edit or MCP Pro `edit_image`. | Use for a still composite; the result is the whole image, not a reusable effect layer. For composed animation, use `vfx_workbench` when visible. |
| Create an animated effect/VFX | MCP `vfx_workbench` when timed parts, a sprite anchor, a trajectory, or reusable effect clips matter; REST `POST /vfx` when MCP is unavailable or the user wants PixelLab's own effects artist. | REST `/vfx` (added 2026-10-19) quotes its cost at submit and charges on delivery, up to 2× the quote; an `effect_id` change saves over the effect. Use raw image animation for free-form motion on an existing image when part/layer controls are not needed. See [VFX Workbench research](pixellab-vfx-workbench-research.md). |
| Isolated reusable VFX/effect sprite | Create Image Pro (`generate-image-v2`) first. | Pro is the reliable route found for effect candidates and variety. Focused aura research found Pixen unreliable: it frequently generated characters, scenes, emblems, platforms, central objects, or fully top-down compositions, and its rare good sheets did not repeat consistently. See the [character-aura research spike](pixellab-character-aura-prompt-research-spike.md). |
| Reduce colors / quantize palette | REST v2 `POST /reduce-colors` or MCP `reduce_colors` (0.1 generations; `num_colors` 2-256 or a `palette_image`, plus ordered `dithering`). Pass all frames of an animation or all directions of a character in one call so they share one palette. For file-level palette clamps, indexed conversion, bit-depth conversion, or document palette replacement on local copies, use the agent-facing `aseprite-cli.md` contract. | Added to the public API, first seen in the 2026-09-08 refresh; before that this was an editor-only workflow. All frames in a call must be the same size, with a 512x512 total pixel budget across them. The response includes the resulting palette as a 1px strip — feed it back as `palette_image` to lock later frames to it. Aseprite's observed `quantize-image` operation remains an undocumented internal endpoint. |
| Unzoom pixel art | REST v2 `POST /unzoom` or MCP `unzoom_image` (0.1 generations), only for genuinely upscaled pixel art. | Inspect native scale first; blanket reference preprocessing is overbroad. Minimum 256x256 input, maximum area 2048x2048; RGB grid detection composites transparency onto white, so disclose alpha-loss/recovery risk and verify the result. A detected grid on a painting does not prove a valid native pixel grid. Aseprite's observed `unzoom-pixelart` remains an undocumented internal endpoint. |
| Try on garment/item | Website Try on for single-image compositing; MCP `transfer_outfit` when visible or REST `transfer-outfit-v2` for animation-frame outfit transfer. | Do not treat either as isolated layer extraction. |
| Reshape | Website Reshape or closest documented edit/character route after checking current docs. | Website docs require exactly 64x64 canvas; no public REST v2/MCP reshape endpoint was documented. |
| Pixel correction / clean-up | REST v2 `POST /correct-pixelart` or MCP `correct_pixelart` (0.1 generations; `strength` 0.0-1.0, default 0.1). | Added to the public API, first seen in the 2026-09-08 refresh. Sharpens edges, drops stray and anti-aliased pixels, and tightens the palette without resizing; maximum area 1024x1024 and transparency is preserved. Unzoom an upscaled sprite first — correction keeps it on whatever grid it arrives on. Aseprite's observed `correct-pixelart` operation remains an undocumented internal endpoint. |
| Prompt enhancement | REST v2 matching enhance endpoint; agent-side fallback. | Low-cost prompt prep. Pick the enhancer that matches the asset type; do not use them as generic optimizers. |
| Map image or level concept | REST v2 image/background route unless the user needs Map Workshop behavior. | A visual map concept is not the same thing as a website Map Workshop project; map extension/texture flows are website workflows unless public endpoints are documented. |
| Furnished room with floor plan/doors | MCP `create_room` → `get_room`; optional `cut_out_room_furniture`; `list_rooms` when the user asks to find or choose an existing room. | Tier 2+, 20 generations painted plus optional 10 for movable furniture; top-down, isometric, or oblique with view-specific restrictions. MCP-only; see [room workflow](../../skills/pixellab-pip/references/scenes-and-backgrounds.md#furnished-rooms). |
| Game Builder / game-building project | Visible Game Builder workflow for Tier 1+ users; use public MCP project/chat/sandbox helpers only for an explicitly approved project-scoped action. | No public REST v2 Game Builder endpoint is documented. See the [official tutorial/showcase](https://youtu.be/Iaxk_8ftJ5s). |
| Map object | MCP `create_map_object`/`get_map_object` when configured; REST v2 `POST /map-objects` otherwise. | Distinguish map objects from whole maps and terrain tilesets. Map objects are permanent as of the 2026-09-08 docs — the former 8-hour auto-delete is gone — and can be placed on a map with `place_map_object`. |
| Whole map / tile-based map | MCP map tools: `create_map` (seeded from a top-down tileset, or from a tiles-pro/path/building tile group via `tile_group_id`), `edit_map` (`path`/`rect` terrain painting, `dry_run` to preview without saving; empty `ops` attaches blend tilesets without painting), `place_map_tiles` (place, stack, or erase tile-group tiles; `dry_run` supported), `get_map` (ASCII grid), `view_map` (rendered image), `list_maps`, `delete_map`, and `place_map_object`/`move_map_object`/`remove_map_object`/`list_map_objects`. Website Map Workshop for manual work and Godot/Unity export. | Added to MCP, first seen in the 2026-09-08 refresh; there is still no public REST v2 map or map-export surface, so do not invent `/v2/maps...` routes. Two terrains from the same tileset family with no blending set meet at a hard edge (straight seam); `view_map` names the pair and the call that blends it. |
| Balance, usage, async job status | MCP balance/status tools when configured; REST v2 balance/background-job endpoints for code. | Report only what the selected route exposes. |

## Clarify Only For Real Collisions

Ask a short clarification when one phrase maps to multiple PixelLab workflows:

- `tiles`: terrain tileset, sidescroller tileset, isometric tile, tile variants, a connectable path/road set, or a building kit.
- `map`: whole map, map image, map object, tilemap, tileset, or Map Workshop project.
- `object`: prop/item/furniture/weapon vs a character-like being.
- `character animation direction`: default to `south` (down-facing) for the first candidate when direction is unspecified and available; ask if `south` is unavailable or if the desired gameplay-facing direction matters.
- `effect`: static sprite vs animated effect, and reusable object vs one-off image.
- `edit this`: edit target, style reference, identity reference, mask, first frame, or last frame.

Avoid asking for clarification when the normal game-asset meaning is obvious.

## Image Inputs

Text-only requests are valid for many PixelLab generation routes. Do not ask for images just because the user wants an asset.

When images are supplied, infer each file's role from the request and the selected endpoint. Common roles include style reference, identity/reference image, concept image, edit target, mask, palette/color reference, init/source image, first frame, or last frame.
